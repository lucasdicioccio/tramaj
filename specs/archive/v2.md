Tramaj V2 — Typed Values, Constraints, and Module Types
Status

This document specifies the V2 additions to Tramaj.

V2 extends the existing language with:

typed unknown values;
first-class constraints;
restricted constraint expressions;
typing judgments on existing values;
template-local type definitions;
product types and discriminated sum types;
type namespaces carried by imports;
constraint-producing higher-order expressions.

The purpose of V2 is to provide a stable substrate for symbolic values and
constraint-aware analysis without turning the core language into a constraint
solver.

The language remains primarily a language for constructing values and
documents. Analysis, type checking, constraint propagation, and solving are
separate concerns.

1. Design principles

V2 follows these principles:

Unknown values are values.
Types are semantic information, not constraints.
Constraints are first-class values.
Constraint arguments have a deliberately restricted representation.
Concrete and symbolic values may participate in the same constraints.
map remains completely generic and may return constraints.
Types are nominal.
Templates may define their own types.
Types are scoped through modules/imports rather than one global namespace.
Type declarations are part of the portable Tramaj program.
The core language does not prescribe constraint-solving algorithms.
The core language does not require values to be concrete.
2. Values

The V2 semantic value space is extended with unknown values and constraints:

Value
  = Null
  | Boolean
  | Number
  | String
  | Array(List<Value>)
  | Object(Map<String, Value>)
  | Lambda(...)
  | Node
  | Unknown(UnknownValue)
  | Constraint(Constraint)

An unknown value is:

UnknownValue
  name: String
  type: Type

An unknown is not equivalent to null.

For example:

@replicas : Int = ?

introduces a symbolic value whose current concrete value is unknown.

Its semantic value is approximately:

Unknown {
  name = "replicas"
  type = Int
}

The name identifies the binding that introduced the symbolic value.

3. Typed bindings

A computation binding may optionally declare a type:

@name : Type = expr

For example:

@replicas : Int = ?
@count : Int = 3
@title : String = "hello"

The type declaration does not imply that the value is unknown:

@count : Int = 3

contains a concrete value.

Conversely:

@count : Int = ?

contains an unknown value.

A binding therefore has the form:

Binding
  name: String
  type: Type?
  value: Expr

The declared type and the type of the resulting expression must be compatible
according to the applicable type environment.

4. Unknown values

The unknown expression is:

Unknown

and is written:

?

A type annotation on the binding supplies its type:

@x : Int = ?

The Unknown expression itself does not need to contain the binding name.

The binding establishes the identity of the resulting symbolic value.

The type system may later grow richer domains, refinements, or symbolic
representations, but V2 only requires that an unknown have a type.

5. Types

Tramaj uses nominal types.

A type is identified by the declaration that defines it, not merely by having
the same structure as another type.

The core type representation is:

Type
  = NamedType(TypePath)
  | ArrayType(Type)
  | ...

The exact set of built-in type constructors may be extended by the
implementation/specification.

A type path may refer to a locally declared type or to a type exported by an
imported module.

V2 does not use implicit structural typing.

Two separately declared product types with identical fields are still
different types.

6. Type declarations

A Tramaj program may declare types.

Conceptually:

TypeDecl
  name: String
  definition: TypeDef

A type definition is:

TypeDef
  = ProductType
  | SumType

A product type contains named fields:

ProductType
  fields: List<TypeField>

where:

TypeField
  name: String
  type: Type

For example:

type Card = {
  title: String
  author: Author
  items: Array<CardItem>
}

defines a nominal product type named Card.

A template can therefore publish an input contract without depending on a
host-specific type dictionary.

7. Discriminated sum types

A sum type consists of explicitly named variants:

SumType
  variants: List<TypeVariant>

A variant has a name and may contain named fields:

TypeVariant
  name: String
  fields: List<TypeField>

For example:

type Result =
  | Ok {
      value: String
    }
  | Error {
      message: String
      code: Int
    }

defines one nominal type, Result, with two discriminated variants.

The discriminator is part of the type definition.

A value matching the fields of Ok from an unrelated type is not thereby an
Ok value of Result.

The detailed runtime representation of discriminated values is specified by
the value/host semantics, not by structural inference.

8. Type namespaces

Types do not share one global namespace.

A module owns the types it declares and exposes them through its module
interface.

An import result conceptually contains:

ImportResult
  rendered
  vals
  types

rendered and vals have their existing semantics.

types exposes the module's type namespace.

For example:

@foo = import("foo", $ctx)

may expose:

$foo.rendered
$foo.vals.SomeValue
$foo.types.Card
$foo.types.CardItem

The types member is a type namespace rather than an ordinary runtime object.

9. Imported type references

A type may refer to a type owned by an imported module:

@foo = import("foo", $ctx)

@my-var : $foo.types.Card = ?

The semantic type reference identifies the Card declaration belonging to
the module represented by $foo.

Conceptually:

ImportedType
  module: ImportReference
  path: TypePath

This means that two modules can independently define:

Card

without creating a global naming conflict:

@a = import("library-a", ...)
@b = import("library-b", ...)

@a-card : $a.types.Card = ?
@b-card : $b.types.Card = ?

$a.types.Card and $b.types.Card are distinct nominal types even if their
definitions happen to be identical.

10. Types and partial imports

Type information is static module information.

Consequently, an incomplete partial-import may expose its types even when
its runtime values and rendered result are not yet available.

For example:

@foo = partial-import("foo", $ctx)

@card : $foo.types.Card = ?

may be valid even if completing the import requires parameters not yet
available.

types therefore differs from rendered and runtime vals in that it need
not depend on completing the module's runtime computation.

11. Typing judgments

A template may require an existing value to have a particular type without
introducing a new binding.

The syntax is:

require(expr : Type)

For example:

require($ctx.title : String)

or:

@foo = import("cards", $ctx)

require($ctx : $foo.types.Card)

A typing judgment is represented as:

TypingJudgment
  value: ExprRef
  type: Type

The value expression is restricted to an expression whose value can be
identified for typing purposes.

At minimum this includes static references and static field access:

require($ctx : SomeType)
require($ctx.title : String)
require($ctx.author.name : String)

The exact set of permitted expressions may be expanded later.

12. Typing judgments are not constraints

A typing judgment and a constraint have different semantic roles.

require($ctx : Card)

states a type requirement.

constraint("gt", $replicas, 0)

states a semantic relation.

The first participates in type checking.

The second participates in constraint analysis.

A typing judgment MUST NOT be encoded as an ordinary constraint.

For example, a type requirement is not equivalent to:

constraint("is-card", $ctx)

The language's type system and constraint system remain separate.

13. Constraints

A constraint is a first-class value:

Constraint
  name: String
  arguments: List<ConstraintExpr>

It is constructed using:

constraint("name", arg1, arg2, ...)

For example:

constraint("gt", $my-unknown, 10)

or:

constraint("gt", $my-unknown, $ctx.threshold)

The constraint name is a static string.

It identifies an entry in an analyzer/host constraint dictionary.

The language core does not prescribe the meaning of particular constraint
names.

14. Concrete and symbolic constraint arguments

A constraint may refer to both unknown and concrete values.

For example:

@threshold = $ctx.threshold
@count : Int = ?

constraint("gt", $count, $threshold)

or directly:

constraint("gt", $count, $ctx.threshold)

The analyzer may therefore receive a relation between:

a symbolic value;
another symbolic value;
a concrete literal;
a concrete context value;
a structured value containing any of the above.

The presence of a concrete argument does not turn the constraint into a
runtime assertion.

15. Constraint expressions

Constraint arguments use a restricted expression representation:

ConstraintExpr
  = Ref
      path: List<String>

  | Literal
      value: JSON

  | Array
      elements: List<ConstraintExpr>

  | Object
      fields: List<(String, ConstraintExpr)>

  | Field
      target: ConstraintExpr
      name: String

This representation is deliberately smaller than the ordinary Expr AST.

For example:

constraint(
  "shape",
  $x,
  {
    "name": $ctx.name,
    "items": [$a, $b, 10]
  }
)

can be represented entirely as ConstraintExpr.

16. Static references in constraints

A constraint reference may identify any value visible in the current
environment, including $ctx:

constraint("gt", $x, $ctx.threshold)

Static field access is permitted:

constraint("eq", $x.name, $ctx.user.name)

The path remains explicit in the normalized representation.

Dynamic lookup is not initially a ConstraintExpr:

constraint("eq", lookup($x, $field, null), $y)

is therefore not valid merely because lookup is a valid ordinary Tramaj
function.

This restriction allows an analyzer to inspect the identity of referenced
values without executing arbitrary computation.

17. Constraint literals

Constraint expressions may contain ordinary literals:

constraint("gt", $x, 10)

constraint("matches", $name, "^[a-z]+$")

constraint("one-of", $environment, [
  "development",
  "staging",
  "production"
])

Objects and arrays may recursively contain valid constraint expressions.

18. Constraint-expression restrictions

Initially, ConstraintExpr does not contain:

lambdas;
arbitrary function calls;
map;
filter;
fold;
scan;
lookup;
imports;
partial imports;
document construction;
actions;
action adaptation.

These restrictions are intentional.

They mean that once a constraint has been constructed, its semantic content
is inspectable data rather than an arbitrary Tramaj program.

This does not prevent ordinary expressions from producing constraints.

19. Constraints are first-class values

Because Constraint is a Value, it may be:

bound to a variable;
returned by a lambda;
passed to another function;
placed in an array;
placed in an object;
returned from map;
combined with other values using ordinary value operations.

For example:

@c = constraint("gt", $x, 0)

and:

@constraints = [
  constraint("gt", $x, 0),
  constraint("lte", $x, 10)
]

are valid.

Constructing a constraint does not itself invoke a solver.

20. map may return constraints

map retains its ordinary semantics:

map(array, function) → Array<Value>

The function may return any value, including a constraint.

Therefore:

map(
  $items,
  (x) => constraint("gt", $x.value, 0)
)

produces an array of constraints.

This is valid whether $items contains concrete values, symbolic values, or
a mixture of both.

For example:

@items = [
  10,
  $symbolic,
  20
]

@constraints =
  map(
    $items,
    (x) => constraint("gt", $x, 0)
  )

produces conceptually:

[
  Constraint("gt", [10, 0]),
  Constraint("gt", [Unknown("symbolic", ...), 0]),
  Constraint("gt", [20, 0])
]

No special constraint behavior is required from map.

21. Higher-order constraint construction

Because lambdas are ordinary values, constraints may be generated by arbitrary
ordinary higher-order computations, subject to the restrictions on the
arguments used to construct each individual constraint.

For example:

@positive =
  (x) => constraint("gt", $x, 0)

@constraints =
  map($items, $positive)

The lambda itself is ordinary Tramaj.

Its result is a constraint value.

The restriction applies when constructing the constraint's arguments, not to
the lambda that produces the constraint.

22. Constraint collection

The core evaluator does not need to treat constraint construction as a side
effect.

A constraint is simply a value.

Consequently, constraints can be accumulated explicitly:

@constraints =
  concat(
    [
      constraint("gte", $replicas, 1),
      constraint("lte", $replicas, $ctx.maxReplicas)
    ],
    map(
      $items,
      (x) => constraint("valid-item", $x)
    )
  )

An analyzer or host may subsequently collect constraint values from designated
bindings, output values, or another host-defined boundary.

The exact constraint-collection policy is outside the core evaluation
semantics.

23. Constraint analysis

V2 does not specify a solver.

An analyzer may interpret:

@replicas : Int = ?

constraint("gte", $replicas, 1)
constraint("lte", $replicas, 10)

as knowledge equivalent to:

replicas : Int
domain   : 1..10
value    : unknown

The analyzer may additionally:

propagate constraints;
narrow domains;
detect contradictions;
determine satisfiability;
infer further type/domain information.

None of these operations are required from the Tramaj evaluator.

24. Unknown values in Nodes

Unknown values remain ordinary values when embedded in Nodes.

For example:

@replicas : Int = ?

.Deployment(
  replicas: $replicas
)

produces a Node containing:

Element(
  tag = "Deployment",
  attributes = [
    Attribute(
      name = "replicas",
      value = Unknown(
        name = "replicas",
        type = Int
      )
    )
  ],
  children = [],
  annotations = {}
)

There is no separate UnknownNode.

An unknown is a value, not a document node.

25. Node normalization

The Node representation continues to distinguish document structure from
values.

Conceptually:

Node
  = Text
      value: String
      annotations: Annotations

  | Element
      tag: String
      attributes: List<NodeAttribute>
      children: List<Node>
      annotations: Annotations

  | Fragment
      children: List<Node>
      annotations: Annotations

An attribute contains a value:

NodeAttribute
  = Attribute
      name: String
      value: Value

  | Action
      event: String
      key: String
      payload: Value

Consequently symbolic values can occur anywhere ordinary values can occur.

26. Type information and Nodes

The Node representation does not need a parallel type hierarchy.

For example:

Element
  └── Attribute
        └── Unknown(Int)

is sufficient.

If a host or analyzer wants to know that an element is expected to have some
particular semantic type, that information can be represented using the
language's normal type system or annotations rather than introducing
specialized symbolic Node variants.

27. Example: reusable typed template

A template may define its own contract:

type Card = {
  title: String
  author: Author
  items: Array<CardItem>
}

type Author = {
  name: String
  avatar: String
}

type CardItem = {
  id: Int
  title: String
}

require($ctx : Card)

.Card(
  title: $ctx.title,
  author: $ctx.author.name
)

The template is self-contained.

It does not require the host to have predefined knowledge of Card,
Author, or CardItem.

The type definitions become part of the template/module's exported type
namespace.

28. Example: imported template types

A library may export:

type Card = {
  title: String
  author: String
}

A consumer can import the library:

@cards = import("cards", $ctx)

and use the library's type:

require($ctx : $cards.types.Card)

or introduce a symbolic value:

@card : $cards.types.Card = ?

The type remains owned by the imported module.

29. Example: types + unknowns + constraints

A larger example:

@lib = import("deployment", $ctx)

@deployment : $lib.types.Deployment = ?

@replicas : Int = ?

require($ctx : $lib.types.DeploymentConfig)

constraint("gte", $replicas, 1)
constraint(
  "lte",
  $replicas,
  $ctx.maxReplicas
)

@item-constraints =
  map(
    $ctx.items,
    (item) => constraint(
      "valid-item",
      $item,
      $ctx.itemPolicy
    )
  )

.Deployment(
  replicas: $replicas
)

This program contains three different kinds of information:

typing:
  ctx : DeploymentConfig
  deployment : Deployment

symbolic values:
  replicas : Int, unknown
  deployment : Deployment, unknown

constraints:
  replicas >= 1
  replicas <= ctx.maxReplicas
  valid-item(item, ctx.itemPolicy)

They remain distinct throughout evaluation.

30. JSON serialization

The V2 AST and semantic value representations remain JSON-serializable.

The serialized representation must preserve:

type declarations;
nominal type identity;
type references;
typed unknown values;
typing judgments;
constraints;
normalized constraint expressions;
Nodes containing symbolic values.

Source locations remain implementation-specific and are not part of the
normative AST.

A consumer that only needs to analyze symbolic values should therefore be able
to consume the serialized AST without implementing Tramaj's parser.

31. Type identity

Type identity is nominal.

A type is identified by its defining module/type declaration.

Therefore:

A.types.Card

and:

B.types.Card

are distinct types unless an explicit compatibility mechanism says otherwise.

The fact that both types have:

title : String
author : String

does not make them interchangeable.

How a host establishes compatibility between a host-native type and a Tramaj
type is outside the core language.

32. Analyzer boundary

The intended architecture is:

             Tramaj program
                    │
                    ▼
              Parse / AST
                    │
                    ▼
                Evaluate
                    │
          ┌─────────┴─────────┐
          │                   │
       concrete             symbolic
        values                values
          │                   │
          └─────────┬─────────┘
                    ▼
              Node / Values
                    │
                    ▼
                 Analyzer
              ┌─────┴─────┐
              │           │
             types    constraints
              │           │
              └─────┬─────┘
                    ▼
             inferred knowledge

The evaluator does not need to know how a constraint is solved.

The analyzer does not need to reimplement document construction.

This separation is a central V2 design goal.

33. Future extensions

V2 deliberately leaves room for:

richer type constructors;
generic types;
additional product/sum features;
pattern matching;
richer discriminated-union analysis;
type compatibility declarations;
domains attached to symbolic values;
constraint propagation;
symbolic arithmetic;
solver integration;
richer analyzer-defined constraint vocabularies;
type and domain annotations on Nodes and values.

These should extend the existing representations rather than turning ordinary
expressions into solver-specific syntax.

The core principle remains:

Tramaj describes values, documents, types, and relations. It does not
prescribe how an implementation must solve those relations.
