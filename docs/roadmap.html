Roadmap

No package in this repository has had a stable release yet, and the language itself is still settling — see the repository README for where the language grammar stands. This page is about something narrower: which implementations of tramaj exist, and which are wanted next.

Where things stand today

Two independent implementations target the same grammar and are checked against a shared, language-neutral conformance corpus — template/context/expected-output triples that both must reproduce byte-for-byte, per case, in both concrete and symbolic evaluation modes. That’s a deliberately strong bar: a case belongs in the corpus only if two independently written implementations can run it identically.

ImplementationLanguageStatus
tramajPureScriptreference implementation, checked against the corpus
tramaj-hsHaskellindependent port, checked against the same corpus

Neither is published to a package registry yet (see the README’s “Publishing” section) — both are used today as workspace/source dependencies. See Integrating tramaj for what’s actually usable from each right now, including the fold each one does or doesn’t ship.

Desired: native implementations for JS, Python, and Rust

For a host in JavaScript, Python, or Rust, Integrating tramaj currently recommends shelling out to tramaj-cli and writing a fold over its JSON output — a real, usable path, but a subprocess boundary rather than a native library. A native implementation in each of these languages is desired, so that hosts in these ecosystems get the same thing PureScript and Haskell hosts already have: an in-process parser and evaluator, with no subprocess and no JSON round-trip required just to get a Node.

LanguageWhy it's wanted
JavaScript / TypeScriptan installable npm package usable directly in a browser or Node host, in place of shelling out to tramaj-cli or compiling a PureScript wrapper
Pythonnative use from data pipelines, notebooks, and backend services already written in Python, without a Node/PureScript toolchain as a runtime dependency
Rusta dependency-light, embeddable core for performance-sensitive or WASM-targeted hosts

None of these exist yet — this is a wishlist, not a schedule. There’s no committed timeline or assigned owner for any of the three.

What “done” looks like for a new implementation

tramaj-hs is the template to follow, since it’s the one implementation that was added after the language had already settled on a normative spec and output format. A new implementation is considered on par with the existing two once it:

  • implements the grammar and evaluation rules in reference.md, including the static restrictions that make imports, action keys, and ctx(...) paths analyzable without evaluation (see Properties);
  • encodes and decodes the Node AST exactly per node-json.md, including the round-trip guarantee (decode(encode(n)) == n);
  • passes every case in the conformance corpus, in both concrete and symbolic mode, byte-for-byte against expected.json;
  • optionally, but ideally: a fold analogous to tramaj-halogen’s foldToHalogen for at least one popular rendering target in that ecosystem (e.g. a DOM fold for JS, a common Python templating output for Python).

The v3 (?/!, v3-symbols.md) and v4 (%, v4-types.md) extensions are both shipped and part of the same conformance bar — a new implementation isn’t considered complete while targeting only the v2 core.

Contributing an implementation

If you’re taking on one of these, the corpus is the fastest way to find out what you got wrong: it’s meant to be run against a from-scratch implementation just as it’s run against the two that exist, and a case that byte-for-byte matches both tramaj and tramaj-hs today is a strong signal your evaluation semantics agree with theirs. Open an issue on the repository before investing heavily in one — coordinating on which language is being worked on avoids duplicate effort.
